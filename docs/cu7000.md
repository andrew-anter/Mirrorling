# Samsung CU7000 (2022) — protocol findings

Reference unit: Samsung 58CU7000 (Tizen 2022, advertised model `UAU7000`), firmware
`T-KSU2EUABC-2301.1`, observed 2026-10-29. Device-identifying fields — the mDNS service name,
AirPlay device ID/MAC, and host machine — are redacted. For installation, pairing, casting and
troubleshooting, see the [project README](../README.md).

## Identity (from live mDNS TXT, `_airplay._tcp`)

```
name      = <redacted>
model     = UAU7000            → Samsung 58" Crystal UHD CU7000 (2022)
firmware  = fv=p20.T-KSU2EUABC-2301.1  (Tizen)
features  = 0x7F8AD0,0x38BCF46
flags     = 0x244
deviceid  = <redacted>
srcvers   = 377.30.02
```

The advertised model is the family name, not the retail model: `UAU7000` is what the CU7000
series reports. `mirrorling discover` prints the model/firmware fields; `mirrorling tvs` uses the model
for discovery and shows it in its list.

## What this means for casting from Linux

| Protocol | Available on TV | Linux sender |
|---|---|---|
| AirPlay 2 (HAP pairing + mirroring) | ✅ advertised; used by iPhone/Mac mirroring | ✅ `doubletake` |
| AirPlay video push (URL/media) | ✅ ("AirPlay Remote Video") | partial (pyatv), not used here |
| Miracast / Wi-Fi Direct sink | ❌ dropped by Tizen 2022 | — |
| Chromecast built-in | ❌ (Samsung TVs don't ship it) | — |
| SmartThings/Tap View mirroring | ✅ but Samsung-device-only | ❌ no Linux client |

Conclusion: AirPlay 2 mirroring via doubletake is the only wireless-desktop path into this TV.

## Sender side (doubletake, verified in source and live)

- Pairing: SRP-6a with an on-TV PIN. Credentials are cached at
  `~/.config/doubletake/credentials.json` (directory `0700`, file `0600`); doubletake's `-creds`
  flag relocates the file and `-cred-backend keyring` can use a Secret Service keyring instead.
  mirrorling uses the default file path.
- Stream: RTSP/HTTP setup, ChaCha20-Poly1305 encrypted H.264 over TCP, timing via
  receiver-initiated NTP on local UDP `N`, audio control `N+1`, audio data `N+2`;
  `-port-range 60000-60010` is pinned in the mirrorling config.
- Audio: the receiver's advertised `supportedFormats.screenStream` mask decides ALAC (built in)
  versus AAC-ELD (needs a libfdk-aac build tag). The default build works with this TV; the
  system default output is followed at each stream start via `device=@DEFAULT_MONITOR@`.
- Capture: Wayland via `org.freedesktop.portal.ScreenCast` → PipeWire fd.
  xdg-desktop-portal-hyprland (XDPH) 1.4.1+ *does* support portal restore tokens, but its stock
  share-picker only requests one when `screencopy:allow_token_by_default = true` is set in
  `~/.config/hypr/xdph.conf` (off by default). Mirrorling does not depend on that setting: it
  installs its own headless picker as `screencopy:custom_picker_binary` and persists the monitor
  choice in its own config. See [Monitor selection](../README.md#monitor-selection).
- Daemon mode (`-daemonize`) runs in the foreground and serves `$XDG_RUNTIME_DIR/doubletake.sock`;
  `mirrorling start` wraps it in a transient systemd user unit named `mirrorling` for journal logs.

## Quirks observed on this unit

- Standby removes the TV from the network (no mDNS, no casting). Power it on first; a stale avahi
  cache entry can outlive it, so mirrorling probes the advertised AirPlay port before calling a TV
  live.
- The on-TV PIN is short-lived: entering it ~45 s after it appears fails with SRP `M4 error: 2`;
  ~17 s works. Re-run `mirrorling pair` and type the code promptly.
- Receiver canvas in auto mode: 1920x1080 H.264 group even though the panel is 4K. HEVC and the
  maximum canvas are opt-in (`-video-codec hevc`); 4K60 stalls this TV's Wi-Fi link, while 4K30
  HEVC was stable.
- The AirPlay port is dynamic (observed 51820, not 7000), so the sender resolves it from mDNS.
- Latency: auto profile ≈ 75 ms video lead / 85 ms audio lead on wireless; override with
  `-target-latency-ms` (via `MIRRORLING_EXTRA_FLAGS`) if lip-sync drifts.
- Mid-session `SET_PARAMETER volume` (daemon mute) is rejected by this firmware (HTTP 500). The
  sender also never writes the volume at session start anymore: doing so commanded full scale, and
  Tizen restores its start-of-session volume snapshot when the session closes — which is what made
  the TV jump to 100% after a cast. Use the TV remote.
- DRM-protected surfaces (e.g. Netflix in a browser) are captured as black: the portal cannot
  capture protected content.
